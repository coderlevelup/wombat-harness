# gemma3:1b on a real Mac run, and a reproduction, 2026-10-18

What happened when the author ran `wombat-tui --model gemma3:1b` on a Mac, what a reproduction here shows, and what it taught
us about the harness. **A self-reported run plus 20 reproduction runs on one tiny task; not a benchmark.**

## The run on the Mac (self-reported, with two screenshots)

- Setup, exactly: `/tmp/wombat-demo` with `calc.py` containing only `def add(a, b): return a - b` and `test_calc.py` with the single test
  `assert add(1, 2) == 3`. Prompt: "The test in test_calc.py is failing. Find the bug in calc.py and fix it, then run the tests." Code: the branch
  as it stood **before** the pydantic-ai work (`pip install -e '.[tui]'`, so by inference the `builtin` engine); commit not recorded.
- It ran, but the model did not complete the task. Per the author: it **got stuck first because pytest wasn't installed** (the model tried to
  install it, which failed); **pre-installing pytest made it work better**, though the task still did not complete.
- What the screenshots show: the model read `test_calc.py` first, said "the code is already correct", then proposed editing the **test**
  (changing `== 3` to `== 1`) and called `list_dir` on a *file* path. After each `n` (deny) it wrote "What do you want me to do with the
  file?" and **carried on with its next action**: the author wanted to type an instruction but the harness gave no chance (see below).

## Reproduction here (current code, the author's exact project, pytest installed)

Five runs on each of `builtin` and `pai-native`, `yolo` mode, 12 steps, judged by `judge` in `reports/compare_engines.py`: hidden checks that
`add` really adds, the visible test file unmodified, visible pytest passing, and a reply. Data: `reports/data/gemma3-1b-repro.jsonl`.

| | `builtin` (5 runs) | `pai-native` (5 runs) |
|---|---|---|
| Genuine success | 0 | 0 |
| `calc.py` fixed | 0 | 0 |
| Visible pytest passed *by editing the test* | 2 | 1 |
| Runs that edited the test file | 4 | 4 |
| Repeat guard fired / step limit hit | 2 / 2 | 2 / 2 |

Across all 10: the model's first tool call was `read_file test_calc.py` in 8, and it **read `calc.py` at all in only 2**. An earlier batch of 10
(exploratory driver, old success criterion, `reports/data/gemma3-1b-repro-batch1-old-criterion.jsonl`) also had `calc.py` fixed in 0 of 10.

So on this project `gemma3:1b` does not fix the bug on either engine. It looks at the test, concludes the code is fine, and tries to change
the test or loops. This fits the earlier finding that models around 1b to 1.5b are too small for this agent, and the author's run matches it.
It does not say whether a differently prompted harness could get a 1b model through: not tested.

## A flaw in my own success criterion (found here, audited)

The drivers called a run successful when visible pytest passed and the agent replied. In the first batch one run met that by **editing the test**,
with `calc.py` unchanged. That is a false positive. I audited every recorded success in all earlier data files (19 runs across the comparison, the live
Anthropic runs and the `pai-tools` runs): **none had edited a test file, and all edited `calc.py`**, so no earlier reported result changes. The drivers
now use the stricter `judge` (hidden checks plus an unmodified test file), checked by a small test of three scenarios (untouched, genuine fix, test edited).
Earlier reports' "judged by re-running pytest" should be read as "plus this audit".

## Harness gaps this exposed (issue #14)

1. **Denying an action gave no way to redirect the agent.** A denial was fed back as a note, but a turn only ends when the model calls `finish`, so the
   model carried on guessing. **Fixed in this branch:** a denial now ends the turn and returns to the input box, with the denial kept in the history,
   so the next message steers the model. Both engines; unit tests for each; and checked live (Claude Haiku 5.5 on `pai-tools`, `gemma3:4b` on `builtin`):
   after a denial the turn ended, the file was untouched, and the next message was answered with no provider error, which matters because a provider
   rejects a tool call left without a result (the `pai-tools` engine closes every pending call in the cut-off batch).
2. pytest missing: nothing warns, and the model tries to install it. Open.
3. The model edits the test to match the bug. Open (prompt rule, flag test-file edits in the approval bar).
4. The person is asked to approve edits already known to fail. Open.
5. Absolute paths in diff headers (`a//private/tmp/...`). Open.

## Caveats

- The Mac run is self-reported; its commit and exact transcript are not recorded, and only two single-frame screenshots exist.
- The reproduction had pytest installed; the author's first run did not. The Mac's other differences (macOS, Ollama build, `/private/tmp` paths) were not reproduced.
- 20 runs of one model on one project, five per engine per batch; no rates or intervals are claimed. `temperature` 0.2.
- The denial fix was verified live on two models once each, plus the unit tests; not under a long session.
